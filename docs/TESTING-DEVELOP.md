# Как развернуть develop-версию NPMOS и что проверить руками

Документ для команды: как поставить свежую сборку на свой сервер или ноутбук и что проверить самому сверх автотестов CI. Состояние на конец фазы 1.

## 1. Какая версия где лежит

| Источник | Что там | Когда использовать |
|---|---|---|
| Docker Hub `opensophy/npmos*:develop` | Сборка из ветки `work` | Обычная проверка: ничего собирать не нужно |
| Локальная сборка `local/npmos*:dev` | Любая ветка, в том числе непослитая | Если изменения ещё не в `work` |
| Dev-стек (`compose.dev.yaml`) | Upstream-образ NPMplus + наш backend и frontend из исходников | Разработка интерфейса и backend. Агент берётся из Hub, поэтому для проверки WAF не подходит |

> **Важно.** Тег `develop` в Docker Hub обновляется только после слияния в `work`. Изменения фазы 1 пока лежат в `claude/practical-ptolemy-ulj2e4`. Чтобы проверить их из Docker Hub, сначала слейте ветку в `work` и дождитесь зелёного CI: задача «Images (amd64) + closed-network test» опубликует образы, затем соберётся манифест `npmos multi-arch manifest`. Без слияния подходит только вариант Б (локальная сборка).

## 2. Что нужно на машине

- Linux x86_64 (amd64). Образы open-appsec собираются только под amd64, arm64 экспериментальный.
- Docker Engine 26+ и Docker Compose 2.23+ (`docker version`, `docker compose version`).
- Свободные порты 80, 443 и 81. Другие порты задаются так: `NPMOS_HTTP_PORT=8080 NPMOS_HTTPS_PORT=8443 NPMOS_ADMIN_PORT=8181`.
- Около 10 ГБ на диске для образов и томов.
- Если на хосте нет IPv6: `NPMOS_DISABLE_IPV6=true` перед каждой командой `docker compose` (или `export NPMOS_DISABLE_IPV6=true`).
- Для варианта Б нужен интернет на время сборки: GitHub, Docker Hub, Alpine, npm. Сама установка интернета не требует.

## 3. Вариант А: образы из Docker Hub

```bash
git clone https://github.com/opensophy-projects/npmos && cd npmos
git checkout work                       # ветка, из которой собран тег develop

docker compose -f deploy/compose.yaml pull
docker compose -f deploy/compose.yaml up -d
docker compose -f deploy/compose.yaml ps   # npmos и postgres должны быть healthy
```

Версии всех образов закреплены в `deploy/.env` (`NPMOS_VERSION=develop`). Другой тег задаётся так: `NPMOS_VERSION=<тег> docker compose ...`.

Проверить, что скачалась свежая сборка: время создания образа должно совпадать со временем последнего зелёного CI в `work`.

```bash
docker image inspect opensophy/npmos:develop --format '{{.Created}}'
```

## 4. Вариант Б: собрать образы самому

```bash
git clone https://github.com/opensophy-projects/npmos && cd npmos
git checkout claude/practical-ptolemy-ulj2e4      # или любая другая ветка

scripts/build-images.sh                            # все 5 образов, тег local/<имя>:dev
NPMOS_REGISTRY=local NPMOS_VERSION=dev docker compose -f deploy/compose.yaml up -d
```

Первая сборка `npmos` (nginx из исходников) и `npmos-appsec-agent` (C++) занимает 30–60 минут на каждый образ. Остальные собираются за минуты. Повторные сборки идут из кэша Docker. Отдельные образы: `scripts/build-images.sh npmos appsec-agent`.

Автотест закрытого контура тот же, что в CI, на собранных образах:

```bash
NPMOS_REGISTRY=local NPMOS_VERSION=dev scripts/test-airgap.sh
```

## 5. Первый вход

1. Откройте `https://<адрес-сервера>:81`. Сертификат самоподписанный, браузер предупредит.
2. Создайте первого администратора. Пароли сервисов, ключи CrowdSec и токен `npmos-control` уже сгенерировал `npmos-init`; `.env` и ручные пароли не нужны.
3. Язык переключается флажком справа вверху.

## 6. Тестовый сайт за прокси

В прод-стеке тестового сервиса нет. Самый простой способ: `whoami` во внутренней сети стека. Он отвечает заголовками запроса, поэтому заодно видно реальный IP клиента.

```bash
docker run -d --name test-upstream --network npmos_internal traefik/whoami
```

Можно взять сайт посложнее, как в `docs/tutor.md`:

```bash
docker run -d --name juice-shop --network npmos_internal bkimminich/juice-shop   # порт 3000
```

В GUI: «Хосты → Proxy Hosts → Добавить», домен (например `test.local`), схема `http`, хост `test-upstream`, порт `80` (для juice-shop: `juice-shop`, `3000`).

Если домена нет, отправляйте запросы с подменой заголовка Host:

```bash
curl -s -H 'Host: test.local' http://<адрес-сервера>/
```

## 7. Обновление уже развёрнутой develop-установки

```bash
git pull
docker compose -f deploy/compose.yaml pull     # для варианта Б: scripts/build-images.sh
docker compose -f deploy/compose.yaml up -d
```

- `npmos-init` запускается при каждом `up` и только дополняет недостающее: новые секреты (например, ключ bouncer `appsec` для агента) и каталоги. Существующие пароли и данные не трогает.
- Миграции БД (`npmos_waf_*`, `npmos_waf_custom_policy`) применяются при старте `npmos`.
- Новые тома (`appsec-model`) compose создаёт сам.

Начать с нуля (удалятся **все** данные: хосты, сертификаты, пользователи, БД, обучение агента):

```bash
docker compose -f deploy/compose.yaml down -v
```

## 8. Атаки для проверки WAF

```bash
H='Host: test.local'; T=http://<адрес-сервера>
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" "$T/?q=hello"                                    # норма: 200
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" "$T/?id=1%27%20OR%20%271%27=%271"                # SQLi
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" "$T/?q=%3Cscript%3Ealert(document.cookie)%3C/script%3E"  # XSS
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" "$T/?file=../../../../etc/passwd"                # path traversal
curl -s -o /dev/null -w '%{http_code}\n' -H "$H" "$T/?cmd=;cat%20/etc/passwd"                     # RCE
```

Ожидается: в Prevent-Learn атаки получают `403`, в Detect-Learn — `200`; нормальный запрос всегда `200`. После смены режима агенту нужно до 30 секунд.

## 9. Что уже проверяет CI (руками повторять не обязательно)

Каждый push прогоняет `scripts/test-airgap.sh`: весь стек в сети без интернета, сценарии в `deploy/test/smoke.sh`.

- Стек поднимается без интернета, ни один сервис не пытается выйти в облако (Check Point, CrowdSec Console/CAPI, Gravatar, проверка версий).
- Прокси работает, upstream видит реальный IP клиента.
- «Система → Сервисы»: список, логи, перезапуск postgres с переподключением, пересоздание nginx-конфигов, диагностический архив. `socket-proxy` и `npmos-control` перезапустить нельзя.
- Включение WAF переключателем в GUI (перезапуск npmos с attachment).
- Агент применяет сгенерированную политику **без регистрации в облаке Check Point**.
- Prevent-Learn: SQLi и XSS получают 403, нормальный запрос проходит. Detect-Learn: SQLi проходит.
- «WAF → События»: блокировка видна как Prevent, обнаружение — как Detect.
- «WAF → Агент»: сохранение настроек перезапускает агент, настройки применяются, атаки после этого блокируются. Агент забирает решения из локального CrowdSec.
- «Политика (эксперт)»: исключение для IP клиента пропускает атаку, без исключения снова 403.
- Сессия переживает перезапуск npmos.

## 10. Что стоит проверить самому

Ниже то, что CI не покрывает или покрывает частично. Отметьте, что прошло, и пришлите проблемы с диагностическим архивом (п. 11).

### Установка и обновление
- [ ] Чистая установка по варианту А на реальном сервере. Чистая установка по варианту Б, если ветка ещё не слита.
- [ ] Обновление поверх прошлой develop-установки (п. 7): данные, пользователи и хосты на месте, WAF-вкладка у старых хостов показывает «Выключен».
- [ ] Хост без IPv6 (`NPMOS_DISABLE_IPV6=true`) и нестандартные порты.
- [ ] Перезагрузка сервера: стек поднимается сам, WAF остаётся включённым, политика применяется.
- [ ] Полностью без интернета на своём сервере: отключите внешнюю сеть (или запретите исходящий трафик в firewall) и перезапустите стек. Должно работать всё, кроме выпуска Let's Encrypt.

### WAF по шагам из `docs/tutor.md`
- [ ] «WAF → Агент»: включить WAF. После перезапуска (около 30 с) видно «Управление: локально, без облака» и время «Политика применена».
- [ ] Хост: вкладка «WAF» в окне хоста, режим Detect-Learn, минимальная уверенность High. В списке хостов появляется бейдж Detect.
- [ ] Атаки из п. 8 в Detect-Learn проходят (`200`) и видны в «WAF → События → Важные события». Проверьте карточку события: IP, тип атаки, «Что обнаружил WAF», исходный JSON.
- [ ] Переключить хост на Prevent-Learn: атаки получают `403`, нормальные страницы сайта (походите по juice-shop) не блокируются.
- [ ] **IP источника в событиях** — настоящий IP клиента, а не адрес Docker-шлюза. CI проверяет это только внутри Docker-сети, а вы проверьте с другой машины.
- [ ] Custom locations: добавьте хосту location (например `/api`) и поставьте ему свой режим или «Выключено». Атака на `/api/...` ведёт себя по режиму location, атака на `/` — по режиму хоста.
- [ ] Выключение и удаление хоста: его правила пропадают из политики («WAF → Агент → Показать YAML»).
- [ ] Ложные срабатывания на ваших реальных сайтах в Detect-Learn: что попадает в «Важные события» при обычной работе.

### «Политика (эксперт)»
- [ ] Исключение по IP из примера на странице (впишите свой IP): атаки с вашего IP проходят в Prevent-Learn, с другого — блокируются.
- [ ] **Исключение по стране** (`key: countryCode`, пример 1 из `docs/tutor.md`) не проверялось: агенту, возможно, нужна GeoIP-база. Проверьте и напишите результат.
- [ ] «Проверить» показывает diff, ошибка YAML показывается с номером строки, «Откатить» возвращает старую версию.
- [ ] Неудачный, но синтаксически верный фрагмент (например, несуществующая практика в `policies.default`): что делает агент и что видно на странице «WAF → Агент». Агент политику не применит. Важно понять, насколько понятно это показано.

### «WAF → Политика» (фаза 5)
- [ ] **Исключение из события:** откройте заблокированную атаку в «WAF → События» → «Создать исключение». Уберите лишние условия (например, параметр), просмотрите изменения и примените. Атака с этого IP проходит; на вкладке «Версии» откатитесь на предыдущую версию — снова блокируется.
- [ ] **Шаблоны:** в меню WAF строки на «Хостах» выберите «Строгий». Проверьте, что ответ — страница блокировки и что срабатывают более слабые атаки (уверенность «средняя»). Верните «Рекомендуемый».
- [ ] **Ограничение частоты** (нужен образ агента из CI этой ветки, с патчем 0002): создайте объект на вкладке «Ограничения частоты» (URI `/login`, 3 в минуту, «Блокировать»), назначьте его хосту в «Свои объекты». Формат файла станет v1beta2; пятый запрос к `/login` за минуту получает 403.
- [ ] **Импорт/экспорт:** экспортируйте политику в v1beta2, импортируйте обратно — план без ошибок, всё «обновляется». Импортируйте свой `local_policy.yaml`, если он есть.
- [ ] Что непонятно в редакторе объектов: подписи полей, подсказки, какие поля стоит добавить (сейчас нет тонких настроек IPS/файлов и антибота — это Premium).

### «WAF → Агент → Настройки агента»
- [ ] **Fail-close** (CI не проверяет): выключите fail-open и сохраните, затем `docker stop npmos-appsec-agent`. Запросы к защищённому хосту должны отклоняться, к незащищённому — проходить. Включите fail-open и повторите: запросы проходят без проверки. Не забудьте `docker start npmos-appsec-agent`.
- [ ] **Репутация IP из CrowdSec** (CI проверяет только, что агент забирает решения): включите в режиме Prevent, забаньте IP тестовой машины и проверьте, что запросы с неё блокируются агентом. Снимите бан.
  ```bash
  docker exec npmos-crowdsec cscli decisions add --ip <IP> --duration 10m
  docker exec npmos-crowdsec cscli decisions delete --ip <IP>
  ```
  CLI здесь только для теста: GUI управления CrowdSec появится в фазе 7.
- [ ] **Advanced-модель**: загрузите настоящий `open-appsec-advanced-model.tgz`, если он у вас есть. Агент перезапускается и работает, в логах агента («Система → Сервисы → appsec-agent → Логи») видна распаковка. С настоящим файлом не проверялось.
- [ ] Пока саму модель больше не используют, удалить её из GUI нельзя (распакованная модель остаётся в томе агента). Если это нужно, скажите: добавлю.

### Переезд с open-appsec-npm
- [ ] Если у вас есть установка open-appsec-npm: положите её `local_policy.yaml` в том `appsec-localconfig` до первого старта NPMOS (или перенесите базу хостов). Режимы хостов должны импортироваться (правила `npm-managed-*`), а исходный файл — сохраниться в `/data/npmos/waf/policy-backups` с пометкой `before-npmos`. Проверялось только в dev-стеке.

### Интерфейс
- [ ] Русский и английский, светлая и тёмная тема на новых страницах: «WAF → События», «WAF → Политика», «Политика (эксперт)», «Агент», «Система → Сервисы».
- [ ] Пользователь без прав администратора: не видит разделы WAF и «Сервисы», вкладка WAF в хосте показывается по его правам на хост.
- [ ] Узкий экран и телефон.

## 11. Если что-то не так

- «Система → Сервисы → Диагностика» скачивает архив с состоянием и логами всех сервисов, без секретов. Приложите его к issue.
- Логи отдельного сервиса: «Система → Сервисы → <сервис> → Логи» или `docker compose -f deploy/compose.yaml logs <сервис>`.
- Текущая политика агента: «WAF → Агент → Показать YAML». Её резервные копии (20 последних): `/data/npmos/waf/policy-backups` в томе `npmos-data`.

## 12. Известные ограничения на конец фазы 1

- «События» читают последние 16 МБ каждого лог-файла агента. Пагинация на сервере, фильтры и хранение в БД будут в фазе 4.
- Уровень отладки агента в GUI появится в фазе 4 («Система → Диагностика»).
- Настройки агента применяются его перезапуском. При fail-close защищённые хосты на эти несколько секунд недоступны.
- Управление CrowdSec из GUI (баны, hub, сценарии) — фаза 7.
- Обучение и тюнинг (smartsync, tuning) запущены, но в GUI их пока нет — фаза 8.
