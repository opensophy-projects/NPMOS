# Обучение агента open-appsec без ложных срабатываний и обмен знаниями между установками

Исследование перед фазой 8. Источники — код в `reference/` (open-appsec `634f840`, smartsync `8e4d8b6`,
smartsync-tuning `f349745`), пути указаны относительно `reference/openappsec/components/security_apps/waap/waap_clib/`
и `reference/smartsync*/`. Что ещё нужно проверить на стенде — в разделе 8.

## 1. Что на самом деле «учится»

Главное, что нужно понимать: **веса модели локально не меняются**. Оценка запроса (0–10) считается моделью,
которая приходит готовой: базовая встроена в агент (`resources/*.data`), advanced — файл с портала open-appsec.
Локальное «обучение» — это **фильтр индикаторов по каждому активу** (хост/локация в политике): агент запоминает,
какие индикаторы атак нормальны для конкретного параметра конкретного приложения, и перестаёт учитывать их в оценке.

| Что учится | Где в коде | Файл в shared-storage | Порог (smartsync) |
|---|---|---|---|
| «Индикатор X нормален в параметре P» | `KeywordIndicatorFilter`, `ConfidenceCalculator` | `/<tenant>/<asset>/<тип>/remote/confidence.data` (от агентов), `processed/confidence.data` (результат) | ≥ 3 разных источника, ≥ 5 интервалов по 2 ч, доля ≥ 0.8 |
| «Тип значения T нормален для P» (html, base64, путь…) | `TypeIndicatorsFilter` | то же, тип `TypesConfidence` | ≥ 10 источников, 5 интервалов по 1 ч |
| То же, но от доверенных источников | `TrustedSourcesConfidence` | `remote/data.data`, `processed/data.data` | сразу, если индикатор пришёл от ≥ `numOfSources` доверенных |
| Сканеры (их трафик не учится) | `ScannerDetector` | `remote/state.data` | источник с индикаторами в ≥ 3 разных параметрах за цикл |
| Решения человека | `TuningDecision` | `/<tenant>/<asset>/tuning/decisions.data` | опрос каждые 30 мин |

Как считается уверенность (`ConfidenceCalculator::calculateInterval`):

- за интервал считаются **разные источники**, у которых индикатор встретился в параметре; если источников меньше
  `minSources` — интервал для параметра пропускается;
- уровень растёт на `100 / minIntervals × (доля / 0.8) × log(число источников)`; индикатор считается нормой при 100;
- интервал без индикатора **уменьшает** уровень (`× 0.8`), т.е. выученное без подтверждения постепенно забывается
  (кроме режима `learnPermanently`, он включён по умолчанию для набора уже выученных значений);
- источники из `ScannerDetector` и всё, что размечено «атака», в расчёт не попадают.

Отсюда первое правило: **агент учится только на разнообразии источников**. Один пользователь, сколько бы он ни
повторял запрос, ничего не «научит» — это и защита от отравления, и причина, по которой маленькие и закрытые сайты
почти не обучаются сами.

## 2. Откуда берутся ложные срабатывания

1. Настоящие данные приложения похожи на атаку: HTML в редакторе CMS, SQL в админке БД, код в форме, длинные
   base64/JWT, пути с `../` в API файлового менеджера, JSON в query.
2. Мало разных источников: внутренний портал на 5 человек, сервис за NAT/балансировщиком (все запросы — один IP),
   API для одного клиента. `minSources = 3` не набирается, параметр не учится никогда.
3. Неверный идентификатор источника: за прокси агент видит один адрес на всех (ложные срабатывания не учатся), либо
   источник берётся из заголовка, который клиент подделывает (см. 3.2).
4. Перевод в prevent до того, как агент выучил приложение (readiness < Graduate).
5. Новая версия приложения добавила параметры — для них обучение начинается заново.

## 3. Риски «обучения» — что может пойти не так

### 3.1. Отравление модели

Если атакующий с ≥ 3 адресов несколько циклов подряд шлёт в параметр одни и те же индикаторы, агент признает их
нормой для этого параметра — дальше настоящая атака в нём будет оцениваться ниже. Встроенные защиты:

- нужна доля ≥ 0.8 от **всех** источников параметра — атакующему надо «перекричать» реальных пользователей;
- `ScannerDetector` исключает источники, которые бьют по многим параметрам (сканеры, фаззеры);
- события с решением «атака» (по значению, параметру, URL или источнику) не учатся вообще
  (`IndicatorsFiltersManager::registerKeywords`);
- выучивается не «пропускать запрос», а «не учитывать индикатор X в параметре P» — другие индикаторы в том же
  запросе по-прежнему поднимают оценку.

Для малого трафика это слабая защита: если реальных пользователей двое, трёх адресов атакующего хватает.

### 3.2. Решения человека, которые опаснее, чем кажутся

| Решение | Что делает агент | Риск |
|---|---|---|
| benign по **источнику** | вес источника = `minSources` (`sumSourcesWeight`): один этот адрес учит модель как три | **самое опасное**: если адрес скомпрометирован, общий (NAT, VPN, прокси) или подделывается через заголовок — любой его трафик становится «нормой» |
| benign по **имени параметра** | уверенность по параметру растёт в 2 раза быстрее (`BENIGN_PARAM_FACTOR`) | широкое: касается любых значений параметра, включая будущие атаки в нём |
| benign по **URL** / **значению** | индикаторы регистрируются от виртуального источника `TuningDecisionSource_*` | узкое: точное совпадение строки; безопасно для значения, умеренно для URL |
| malicious (любой тип) | данные не учатся | безопасно: худший случай — параметр учится медленнее |
| dismiss | ничего | безопасно |

Совпадение решений — **точное по строке** (`TuningDecision::getDecision`): решение по значению `abc` не действует на
`abcd`. Это хорошо для безопасности и плохо для удобства: для «пачки» похожих событий нужны решения по параметру
или URL, а не по каждому значению.

### 3.3. Мгновенные рычаги

Исключения политики (accept/skip по параметру, URL, IP) действуют сразу и **не проверяют содержимое** — это не
обучение, а дыра, если сделать её шире, чем нужно. Поэтому в NPMOS исключение из разметки должно быть
максимально узким (хост + URL + параметр + индикатор), со сроком жизни и с аудитом.

## 4. Безопасный порядок обучения хоста

1. **Источник клиента.** До обучения задать идентификатор источника (объект «Идентификаторы источников» в
   редакторе политики): за доверенным прокси — `X-Forwarded-For` **только** если адрес прокси в списке доверенных
   (`real_ip` в nginx), для приложений с авторизацией — cookie сессии/JWT `sub`. Без этого обучение либо не идёт
   (один адрес на всех), либо подделывается.
2. **detect-learn** на новом хосте. В это время ничего не блокируется, события копятся.
3. **Доверенные источники.** Добавить 2–5 адресов, которые точно чистые и ходят по приложению «как люди»
   (QA, офис, мониторинг сценариев). Для малого трафика это главный способ обучиться: доверенные источники учат
   сразу. Не добавлять общие адреса (NAT провайдера, VPN для всех, адрес балансировщика).
4. **Разметка очереди** (фаза 8): по умолчанию решение «Легитимно» ставится по **значению** или **URL**;
   по имени параметра — только для параметров, где содержимое заведомо свободное (тело статьи, комментарий);
   по источнику — только для адресов, которые уже в доверенных. Атаки помечать «Атака» — это исключает их из
   обучения.
5. **prevent-learn** когда: readiness ≥ Graduate (≥ 7 суток и достаточно запросов, см. `smartsync-tuning`
   `standalone_operations.go`), очередь «серой зоны» за последние сутки пуста или размечена, ложных блокировок в
   detect-режиме нет. Порог `minimum-confidence` — `critical` на старте, затем `high`.
6. **После перевода** — смотреть Detect-события «серой зоны» (оценка 3–6): это то, что агент сейчас пропускает,
   но о чём не уверен.
7. **Новая версия приложения** — временно вернуть хост в detect-learn или следить за новыми параметрами.
8. **Сброс обучения** (уже есть в GUI) — если хост долго учился на мусоре или его отравили.

### Ограничители, которые NPMOS должна добавить в фазе 8

- Решение benign по источнику — только для адресов из «Доверенных источников» или с явным подтверждением
  и предупреждением; для частных/общих адресов (адрес прокси, NAT) — запрет.
- Решение benign по имени параметра — предупреждение «распространится на любые будущие значения».
- Перед записью решения — «что изменится»: сколько событий за 7 дней попадают под решение, сколько источников,
  есть ли среди них события «Атака» или источники с банами CrowdSec (тогда решение блокируется).
- Не предлагать benign для событий, где источник одновременно в банах CrowdSec или был помечен сканером.
- Мгновенное исключение — только узкое и со сроком (по умолчанию 7 суток), затем снимается, если обучение
  подтвердило норму, или продлевается вручную.
- Все решения — в журнале (кто, когда, на что распространяется), отменяемы (undo = удаление строки из
  `decisions.data`).
- Голоса нескольких людей (опция): решение по параметру/источнику вступает в силу после второго подтверждения.

## 5. Можно ли делиться «агентами» и «датасетами» между пользователями

Короткий ответ: **готовым обученным агентом — нет; знаниями о конкретном приложении — да, но только как
предложениями, которые получатель проверяет**. Ниже — что именно переносимо.

| Что | Содержит | Переносимость | Риски |
|---|---|---|---|
| Политика, объекты, исключения (YAML) | правила, URL, параметры | уже есть: экспорт/импорт в редакторе политики | исключение = дыра; надо смотреть diff (уже есть превью) |
| Решения разметки (`decisions.data`) | тип, точная строка, решение | технически просто (JSON) | benign по источнику бессмыслен (чужие IP) и опасен; benign по параметру — широкий |
| Обработанное состояние `processed/confidence.data` | «параметр → набор нормальных индикаторов» + уровни, **без адресов** | технически возможно: файл кладётся в shared-storage, smartsync берёт его за основу | это «белый список индикаторов»: чужой файл может выключить защиту параметров; имена параметров должны совпадать |
| Сырые данные агентов `remote/*.data` | параметр → индикатор → **адреса клиентов** | нет | персональные данные (IP), привязка к конкретному трафику |
| Датасет событий NPMOS | IP, URL, значения параметров, cookies в сэмплах | только после анонимизации | ПДн и секреты в сэмплах (токены, пароли в query) |
| Advanced-модель | веса модели Check Point | нет — распространяется по условиям open-appsec, каждый скачивает сам | лицензия |

### 5.1. Что имеет смысл: «профили приложений»

Ложные срабатывания одинакового ПО (WordPress, Nextcloud, Gitea, 1С-Битрикс, Grafana, Keycloak…) одинаковы у всех:
одни и те же параметры с HTML, SQL, base64. Поэтому полезный и безопасный обмен — **профиль приложения**:

```json
{
  "format": "npmos-learning-profile/1",
  "app": { "name": "wordpress", "versions": ">=6.4 <7" },
  "author": "…", "created": "2026-10-29", "signature": "ed25519:…",
  "items": [
    { "url": "/wp-admin/post.php", "param": "content", "indicators": ["<script", "onerror"], "decision": "benign",
      "reason": "тело записи в редакторе", "evidence": { "sources": 14, "days": 21, "nodes": 3 } },
    { "url": "/xmlrpc.php", "decision": "malicious", "reason": "перебор паролей" }
  ]
}
```

- В профиле нет IP, значений параметров и имён хостов — только путь, параметр, индикаторы, решение и
  «доказательства» в виде чисел.
- При импорте элементы **не применяются**, а попадают в очередь разметки как «предложения из профиля X»;
  администратор принимает пачкой или по одному. Принятое становится обычным решением этого узла.
- malicious-элементы можно принимать автоматически (они только исключают данные из обучения).
- benign — только по URL + параметру, никогда по источнику; индикаторы из «никогда не подавлять»
  (список NPMOS: `union select`, `../` в системных путях, команды ОС и т.п.) отклоняются при импорте.
- Подпись ed25519: администратор добавляет ключи, которым доверяет (свой второй узел, команда, сообщество).
  Без доверенной подписи импорт возможен, но с предупреждением.
- Профиль переносится файлом — работает в закрытом контуре; онлайн-каталог профилей (если когда-то появится) —
  только опцией, как hub CrowdSec.

### 5.2. Между своими узлами

Между узлами одной организации, где приложения одинаковые, можно делиться и решениями `decisions.data`, и
`processed/confidence.data` того же актива — это ровно то, что делает smartsync через общий shared-storage
(фаза 9). До фазы 9 — экспорт/импорт профиля из 5.1 с узла на узел.

### 5.3. Общий датасет для вторичной модели (R&D)

Для «вторичной модели, которая только предлагает метки» (8.3) нужны признаки, а не сырые события:
индикаторы, тип параметра, длина, энтропия, оценка агента, тип атаки, путь с заменой идентификаторов на шаблон
(`/user/123` → `/user/{id}`), метка. Без IP, значений и хостов. Такой датасет можно собирать с нескольких
установок (добровольный экспорт файла), но вторичная модель **никогда** не участвует во inline-вердикте и не пишет
решения сама — её результат только сортирует очередь и предзаполняет кнопку.

## 6. Что это значит для фазы 8 (предложения)

1. Очередь «серой зоны» и группировка — как в ROADMAP; группа = хост + URL-шаблон + параметр + набор индикаторов.
2. Решение по умолчанию — по URL+параметру (через виртуальный источник: одно решение на группу), а не по значению;
   по источнику — только для доверенных.
3. Проверки перед записью решения из раздела 4 («что изменится», конфликт с атаками и банами).
4. Мгновенное узкое исключение со сроком — галочка, включена по умолчанию для benign на хостах в prevent.
5. Экспорт/импорт профиля приложения (5.1) с подписью; импорт → предложения в очереди.
6. Экран «Обучение»: readiness, «что мешает перейти к следующему уровню» (из tuning), доверенные источники,
   число решений, доля ложных срабатываний до/после.
7. Ретеншн партиций `appsec` tuning-сервиса (отложено из фазы 4).

## 7. Чего не делать

- Не «ускорять» обучение снижением `minSources` в smartsync для всех: это прямой путь к отравлению. Для малого
  трафика — доверенные источники и разметка.
- Не размечать benign по источнику адрес прокси/балансировщика/NAT.
- Не импортировать чужие `processed/confidence.data` и `decisions.data` как есть.
- Не делиться событиями с сэмплами (в них бывают пароли и токены).
- Не переводить хост в prevent только потому, что «прошла неделя»: смотреть readiness и очередь.

## 8. Проверить на стенде (спайк фазы 8)

- Tenant/asset ID в standalone: какие значения агент использует в путях shared-storage для хостов NPMOS
  (`npm-managed-*`), где лежит `decisions.data`.
- Что `smartsync-tuning` при `POST /api/v2/assets/{asset}/tuning` не затирает решения, записанные NPMOS напрямую
  (`mergeTuneEvents`), или писать все решения только через его API.
- Фактическое время от решения до изменения оценки (30 мин опроса + интервал обучения).
- Подхватывает ли smartsync подложенный `processed/confidence.data` (нужно для 5.2) и как быстро он «забывается»
  без подтверждения трафиком.
- Работает ли `learnPermanently` для импортированных значений.
