# Политика WAF NginxionS: полностью рабочий v1beta2

Как пользоваться политикой в интерфейсе — [WAF-POLICY-GUIDE.md](WAF-POLICY-GUIDE.md). Здесь — устройство и решения.

Документ описывает, какую политику open-appsec NginxionS должен поддерживать полностью. Каждое поле схемы
либо работает в агенте NginxionS, либо отклоняется проверкой в GUI с понятной причиной. Ни одно поле не
должно молча игнорироваться. План работ — фаза 11 в [ROADMAP.md](ROADMAP.md). Текущее устройство политики
описано в [ADR-0008](adr/0008-waf-policy.md).

**Состояние (ноябрь 2026):** все поля v1beta2 работают (раздел 3). Движки, которые в open-appsec есть только в
Premium или облаке Check Point, NginxionS выполняет своими средствами (раздел 8). Ниже — история фазы 11.

**Фаза 11 выполнена:**

- Доработки агента A1–A9 сделаны. Несколько серверов syslog/CEF, имена и IPv6, которых сам агент не умеет, обслуживает
  ретранслятор NginxionS (раздел 8.5).
- Unit-тесты секций (A10) написаны.
- Генератор всегда пишет v1beta2.
- Действует проверка «нет молчаливых полей».
- Есть сверка применённой конфигурации и новые поля GUI.
- Smoke проверяет перенаправление и правила ограничения частоты.

Расширения `x-nginxions` (раздел 5.2) сделаны в фазе 12.

## 1. Почему это нужно

open-appsec описывает локальную политику в двух синтаксисах:

- **v1beta1** — исходный, на нём работал open-appsec-npm (интеграция в NPM/NPMplus);
- **v1beta2** — новый, в документации помечен как beta.

Схема v1beta2 (`schema-v1beta2.json`, взята у агента) шире того, что агент применяет на самом деле. Сейчас
v1beta2 работает так:

- часть полей агент читает, но в конфигурацию движков не передаёт;
- часть движков есть только в Premium-версии или требует облака Check Point;
- некоторые сочетания полей молча теряются.

В NPMplus с open-appsec-npm политика правилась сырым YAML без проверки. Такие поля просто не работали, и
администратор об этом не узнавал.

NginxionS генерирует политику из своей БД (ADR-0008). Поэтому гарантия нужна на нашей стороне: то, что можно
выбрать в GUI, действительно применяется агентом.

## 2. Как устроено сейчас

- Объекты хранятся в терминах v1beta2. В агент файл уходит:
  - в v1beta1, если политика не использует возможностей только v1beta2;
  - иначе в v1beta2. Такие возможности: ограничения частоты, ответ-перенаправление, IPS, File Security
    (`objects/format.js`, `needsV2`).
- Генератор обходит известные ограничения агента:
  - у практики с ограничениями частоты в каждом следующем правиле своя копия `<практика>.<n>`;
  - защиты «как у правила» в v1beta1 получают копию практики `<практика>.<режим>`;
  - практика ограничения частоты, которая ничего не ограничивает, не пишется в правило по умолчанию.
- Что уже исправлено в коде агента (`openappsec/agent`, метка `NginxionS:`):
  - **все** исключения правила, а не только первое — в обоих синтаксисах;
  - защиты CSRF, раскрытия ошибок и открытого перенаправления;
  - `nonValidHttpMethods`;
  - список `syslogService`/`cefService` из схемы;
  - правило ограничения частоты без `action`/`match` больше не отбрасывается целиком;
  - ограничение частоты для хоста без схемы;
  - стабильные ID ответов (страница блокировки);
  - нейтральные тексты страницы блокировки;
  - конвертер Snort на Node.js (в образе нет Python).

Комментарий в начале `objects/format.js` («v1beta2 применяет только первое исключение») устарел: агент
NginxionS применяет все исключения в обоих синтаксисах.

## 4. Решение

**Формат.** Остаёмся на `apiVersion: v1beta2` open-appsec и доводим агент так, чтобы v1beta2 работал
полностью. Отдельный синтаксис не вводим:

- импорт и экспорт остаются совместимыми с документацией open-appsec и с файлами других установок;
- пример из документации open-appsec у нас работает так, как в нём написано.

Своё расширение схемы добавляем только там, где в v1beta2 нет нужной возможности, а движок агента её
умеет (раздел 5.2):

- поле расширения необязательное и отмечено в `schema-v1beta2.json` как `x-nginxions`;
- агент с исходным кодом open-appsec такие поля игнорирует (неизвестные ключи cereal пропускает);
- экспорт «совместимый v1beta2» убирает их с предупреждением.

**Правило «нет молчаливых полей».** Каждое поле схемы попадает в одну из трёх групп:

1. Работает: агент NginxionS применяет поле так, как описано в документации.
2. Отклоняется: проверка политики (предпросмотр, импорт, API) возвращает ошибку с причиной. Сначала сюда
   относились File Security, Schema Validation, IPS Check Point и Anti-Bot. Теперь их выполняет NginxionS
   (раздел 8), и отклонять больше нечего: эмуляцию угроз (песочницу Check Point) заменяет углублённый статический
   анализ ClamAV.
3. Kubernetes или облако (`configmap`, `appsecClassName`, `policyActivations`, `cloud`, `k8s-service`,
   `autoUpgrade`): допускаются при импорте и выбрасываются с предупреждением.

**Один формат файла для агента.** Генератор всегда пишет v1beta2. Ветка v1beta1 и копии
`<практика>.<режим>` для защит удаляются. v1beta1 остаётся для импорта (open-appsec-npm, старые экспертные
фрагменты) и как формат экспорта.

**Одна практика каждого вида и один триггер на правило.** «Несколько практик в правиле» в агенте не
реализовано, а слияние двух практик неоднозначно: какой порог уверенности, какой лимит размера. Поэтому:

- проверка требует ровно одну практику threat prevention, одну практику access control и один триггер
  журналирования;
- импорт с несколькими элементами показывает в плане, что применится только первый, и предлагает объединить.

### 5.2. Расширения схемы NginxionS (`x-nginxions`)

Добавляются только поверх доработок A1–A10 и только на то, что движок уже умеет:

| Поле | Что даёт |
|---|---|
| `exceptions[].condition[].key`: `method`, `headerName`, `headerValue`, `paramLocation`, `indicator` | Исключения по методу, заголовку, месту параметра, индикатору атаки. Сейчас такие условия отбрасываются |
| `exceptions[].condition[].op`: `equals` (по умолчанию), `not-equals`, `in`, `not-in`, `exist` | Отрицание: «всё, кроме…», например drop для всех стран, кроме RU |
| `customResponses[].headers` (если позволяет attachment) | Заголовки ответа блокировки, например `Retry-After` для 429 |

Каждое расширение сначала проверяется по движку: какие ключи на самом деле сопоставляет WAAP, а какие
только объявлены. До проверки поле в схему не входит.

**Сделано (фаза 12): ключи и операторы условий исключений.**

- Ключи: WAAP собирает `method`, `headerName`, `headerValue`, `paramLocation` и `indicator` для сопоставления
  исключений (`Waf2Transaction::getExceptionsDict`, переопределение параметра в `Waf2Engine.cc`). Генератор
  агента их отбрасывал. Теперь условие переходит в `match` как есть. Имена и значения заголовков WAAP
  приводит к нижнему регистру.
- Операторы: `op` у условия — `equals` (по умолчанию), `in`, `not-equals`, `not-in`, `exist`. Значения одного
  ключа с `equals`/`in` — любое из них; с `not-equals`/`not-in` — ни одно из них (одно условие `not-in`).
  Разные ключи и операторы — все одновременно. `exist` — у ключа есть значение. Раньше `exist` в `MatchQuery`
  не срабатывал никогда: значения сравнивались с пустым списком. Исправлено (`match_query.cc`).
- Неизвестный ключ или оператор агент теперь отклоняет, а не отбрасывает молча; NginxionS проверяет их раньше.
- Экспорт: в v1beta1 исключения с расширением не входят, заголовок файла их называет. В v1beta2 они остаются,
  заголовок предупреждает, что агент open-appsec читает их иначе: оператор как `equals`, без новых ключей.
- Пробный прогон понимает операторы и метод, место параметра, индикатор. Заголовков в событиях нет:
  условие по заголовку даёт «нельзя оценить».

`customResponses[].headers` не сделано: attachment не передаёт свои заголовки в ответ блокировки.

### 5.3. Генератор и проверка (backend NginxionS)

- `format.js`:
  - всегда `asV2`;
  - удалить `needsV2`, `resolveProtections` и выбор v1beta1 в `policy.js`;
  - экспорт v1beta1 остаётся с предупреждениями о том, что теряется.
- `model.js`: проверка «нет молчаливых полей» по разделу 4, ошибки с путём поля и причиной.
- Проверка ссылок:
  - `trustedSources` без `sourceIdentifiers` — предупреждение, пока не сделан A4;
  - несколько практик или триггеров в правиле — ошибка.
- Снимок применённой политики: nginxions-control читает конфигурацию, которую агент сделал из
  `local_policy.yaml` (`/tmp/local_appsec.policy`), а backend сверяет её с ожидаемой (`waf/applied.js`). Сверяются:
  - ассеты хостов;
  - ответы, включая URL перенаправления;
  - число правил ограничения частоты.

  Расхождение показывается на странице «Политика WAF» и на странице агента. Это ловит новые молчаливые поля при
  обновлении open-appsec.

### 5.4. GUI

- Редактор объектов показывает только рабочие поля. Движки Premium выполняет NginxionS (раздел 8), их поля
  есть в редакторе практики.
- Новые поля в редакторе:
  - перенаправление (URL, X-Event-ID);
  - действие и условия правила ограничения частоты;
  - ответ при превышении частоты;
  - несколько файлов Snort;
  - несколько syslog/CEF с протоколом;
  - расширенные условия исключений.
- Импорт показывает в плане по каждому полю «применится», «отброшено (Kubernetes/облако)» или «ошибка».

## 6. Приёмка

- Unit-тесты агента (ctest): на каждое поле раздела 3 — ожидаемая секция конфигурации.
- Unit-тесты backend: проверка «нет молчаливых полей», импорт примеров open-appsec
  (`objects/examples`), экспорт v1beta1.
- Smoke (`deploy/test/smoke.sh`) на живом агенте без интернета:
  - перенаправление: код 302 и `Location` (+ `X-Event-ID`);
  - правило ограничения частоты с условием `url` и своим действием (detect не блокирует, prevent
    блокирует), ответ — `customResponse` правила;
  - одна практика ограничения частоты в двух хостах — работают обе;
  - доверенные источники без идентификатора источника;
  - два файла Snort — срабатывают сигнатуры из обоих;
  - исключение с отрицанием (если расширение принято);
  - событие с `responseCode` в журнале.
- Пример `local_policy.yaml` из документации open-appsec импортируется без молчаливых потерь. Всё, что не
  применится, перечислено в плане импорта.

## 7. Дальше: фаза 12

**Пробный прогон** (`waf/objects/simulate.js`). Решение агента по каждому событию WAF за период вычисляется для
текущей политики и для изменённой. Порядок, как у агента:

1. Правило — по самому длинному `host[/path]`.
2. Исключения правила: значения одного ключа — ИЛИ, разные ключи — И; IP и подсети; регулярные выражения для
   динамических ключей.
3. Режим правила.
4. Минимальная уверенность практики против уверенности события.

ML-анализ не повторяется: событие сохраняет свою уверенность. Условия, которых нет в событиях (код страны),
дают «нельзя оценить», а не догадку. Прогон показывается:

- в предпросмотре каждого изменения политики (24 часа);
- перед переводом хоста в блокировку (7 дней).

**Пробный режим хоста** («Агенты → open-appsec → Обучение», кнопка «Пробный режим»). Хост в режиме обнаружения
остаётся в нём: ничего не блокируется. Выбранное время (от часа до 7 дней) NginxionS оценивает события WAF хоста тем
же прогоном, как их обработал бы режим `prevent-learn`. Отчёт виден и во время пробы. По окончании он сохраняется,
правило уведомлений `waf_trial` сообщает итог, а администратор переключает хост в блокировку или оставляет как есть.
Запускает и закрывает пробу тот, кто может менять режим WAF хоста; у хоста одна открытая проба
(`waf/trial.js`, таблица `nginxions_waf_trial`, API `/api/nginxions/waf/hosts/:id/trial`).

**Расширения `x-nginxions`** — условия исключений по методу, заголовку, месту параметра и индикатору, с отрицанием
и `exist` (раздел 5.2). Дальше по фазе 12 — пункты агента и обучения в [ROADMAP.md](ROADMAP.md).

## 8. Движки Premium в NginxionS

В open-appsec IPS работает только с сигнатурами из облака Check Point, а Anti-Bot, Schema Validation и File
Security есть только в Premium-версии. NginxionS выполняет их сам, на открытых компонентах стека, и не зависит от
интернета. Поля практики остаются полями v1beta2: импорт и экспорт совместимы с open-appsec. В политике, которую
получает агент, Anti-Bot, Schema Validation и File Security выключены (`waf/engines.js`, `forAgent`): их
выполняют CrowdSec и nginx.

### 8.1. IPS: сигнатуры NginxionS

- Движок IPS есть в открытом коде агента, но загружал только зашифрованные сигнатуры Check Point. Теперь он
  загружает открытые (`helper_open_source.cc`), а зашифрованные по-прежнему отклоняет.
- Сигнатуры собираются из правил виртуальных патчей хаба CrowdSec (MIT): коллекции
  `appsec-virtual-patching` и `appsec-generic-rules`. Конвертер — `waf/ips/vpatch.js`, запуск —
  `scripts/update-ips-signatures.mjs`, результат — `openappsec/agent/nginxions/ips-protections.json` в образе.
  Коммит хаба — `CROWDSEC_HUB_REF` в `deploy/openappsec/sources.env`, CI сверяет его с файлом.
- Зоны запроса правила переводятся в контексты IPS: путь, URL, query, метод, заголовки, тело. Значения
  переводятся в ключевые слова `data` и `pcre`. Регулярное выражение значения не выходит за границы значения:
  например, `[^0-9]+` не захватывает соседний аргумент формы.
- Не переводятся 12 правил из 215: им нужны libinjection, base64, длина или подсчёт, а в IPS этого нет. Такие
  атаки всё равно ловят WAAP и AppSec CrowdSec.
- Метаданные сигнатуры:
  - критичность — по классу уязвимости (CWE);
  - уверенность — из правила хаба;
  - влияние на скорость — по тому, используются ли pcre и тело запроса;
  - год — из номера CVE.
- Генератор локальной политики добавляет сигнатуры в секцию IPS, когда практика включает
  `intrusionPrevention` (`policy_maker_utils.cc`). Правила практики отбирают их по критичности,
  уверенности, влиянию и году.
- ctest `ips_ut` проверяет, что каждая сигнатура загружается и компилируется. Smoke проверяет, что
  CVE-2017-9841 блокируется и попадает в события, а `minCveYear` 2018 его пропускает.

### 8.2. Anti-Bot: проверка браузера AppSec CrowdSec

- CrowdSec 1.8 умеет проверку браузера: proof-of-work и отпечаток браузера. NginxionS пишет appsec-config
  `nginxions/policy` (`waf/engines.js`, файл `appsec-configs/nginxions-policy.yaml`) с хуками на правила
  политики, у практики которых включён Anti-Bot.
- Правило определяется так же, как в агенте: побеждает самый длинный `host[/path]`. Хук правила не
  срабатывает на запросы более точных правил.
- `injectedUris` — страницы, на которых браузер проходит проверку. Пройденная проверка ставит cookie. Без
  путей проверка идёт на всех страницах хоста.
- `validatedUris` — пути, которым нужна пройденная проверка:
  - навигация браузера без cookie получает проверку;
  - любой другой запрос без cookie отклоняется.
- Сигналы автоматизации из отпечатка (webdriver, headless и т. п.) складываются в баллы с весами хаба
  CrowdSec. При 75 баллах и больше проверка не засчитывается.
- Проверенные хорошие боты (поисковики и т. п.) проверку не получают: коллекция
  `appsec-bot-challenge-good-bots` поставляется в офлайн-снимке хаба.
- В режиме detect проверка не показывается. Запрос без cookie на `validatedUris` проходит, но пишется в
  события CrowdSec.
- AppSec включается для этого сам, даже если он выключен в «CrowdSec → Настройки». Тогда работает только
  конфиг политики. Нужен баунсер CrowdSec в nginx: он отправляет запросы в AppSec и показывает проверку. Его
  версия поднята до lua-cs-bouncer v1.0.19.

### 8.3. Schema Validation: OpenAPI в AppSec CrowdSec

- Файлы OpenAPI 3 или Swagger 2.0 загружаются в редакторе практики (`waf/schemas.js`). NginxionS хранит их
  у себя и копирует в данные CrowdSec, в `schemas/nginxions/`.
- appsec-config политики загружает файлы (`LoadAPISchemaWithOptions`). Запрос хоста проверяется на
  соответствие одному из файлов практики: путь, метод, параметры, тело.
- `enforcementLevel`:
  - `fullSchema` (по умолчанию) отклоняет и пути, которых нет в файлах;
  - `endpointOnly` проверяет только пути из файлов.
- Detect записывает отказ в события и пропускает запрос.
- Файл, который использует практика, удалить нельзя. Файл, которого нет в NginxionS, становится
  предупреждением политики. Новая загрузка файла с тем же именем перезагружает CrowdSec.

### 8.4. File Security: ClamAV

- Контейнер `clamav` (официальный образ со снимком сигнатур) входит в стек.
- clamd работает, только пока практика с File Security применена хотя бы к одному хосту: его сигнатуры занимают
  около 1 ГБ памяти. NginxionS пишет флаг в общий том и перезапускает контейнер
  (`deploy/clamav/nginxions-clamav.sh`).
- У хоста с File Security nginx проверяет тело загрузки (POST, PUT, PATCH) до того, как отдать запрос дальше
  (`nginxions_files.lua`):
  - отдаёт его clamd потоком (INSTREAM);
  - вирус отклоняет (403, страница блокировки) или только пишет в журнал;
  - находки попадают в события WAF (`waf/files.js`).
- Действие зависит от уверенности сигнатуры ClamAV:
  - вредоносное ПО — высокая;
  - PUA — средняя;
  - эвристика — низкая.
- Загрузка больше `largeFileInspection.fileSizeLimit` (10 МБ по умолчанию) не проверяется. С ней поступают по
  `filesExceedingSizeLimitAction`.
- Если clamd не отвечает (запускается или перегружен), загрузка проходит, как при fail-open агента.
- Сигнатуры:
  - снимок образа;
  - файлы `.cvd`/`.cld`, загруженные в «WAF → Агент → File Security» (без интернета);
  - freshclam, если там разрешены обновления через интернет.
- Критичность (`minSeverityLevel`, по умолчанию «средняя») — по виду вредоносного ПО во второй части имени сигнатуры
  ClamAV (`Платформа.Вид.Имя`). Находка ниже порога пропускается:
  - критическая — Ransomware, Backdoor, Rootkit, Exploit, Worm, Virus;
  - высокая — Trojan, Downloader, Dropper, Loader, Infostealer, Keylogger, Spyware, Malware, Macro, Coinminer, Webshell;
  - низкая — PUA, Adware, Joke;
  - средняя — эвристика, фишинг, упаковщики, тестовые файлы (EICAR) и остальное.
- Архивы (`archiveInspection`), их узнают по первым байтам (zip и документы Office, gzip, bzip2, xz, 7-Zip, RAR, cab, tar):
  - `extractArchiveFiles: false` (по умолчанию) — архив не распаковывается и не проверяется, как у агента;
  - `true` — clamd распаковывает и проверяет архив не больше `scanMaxFileSize`, более крупный проходит без проверки;
  - `archivedFilesWithinArchivedFiles` — действие для zip-архива, в котором лежит архив (по именам его файлов);
  - `archivedFilesWhereContentExtractionFailed` — действие для архива, который clamd не смог открыть: зашифрован
    (`AlertEncryptedArchive`) или превышены его лимиты (`AlertExceedsMax`).
- Файл без имени (`unnamedFilesAction`) — загрузка двоичного типа, у которой нет имени: нет `filename` в
  `Content-Disposition`, путь не кончается именем файла (`/upload/report.pdf`), а в multipart — часть со своим
  `Content-Type`, но без `filename`. Текст, формы, JSON и XML файлами не считаются.
- Эмуляция угроз (`threatEmulationEnabled`): песочницы Check Point нет, вместо неё — углублённый статический анализ
  clamd (`AlertOLE2Macros`, `AlertBrokenExecutables`, `AlertBrokenMedia`, `AlertPartitionIntersection`). clamd
  ищет это всегда, а nginx учитывает такие находки только у практик с эмуляцией: как находки высокой уверенности.

### 8.5. Syslog и CEF: ретранслятор NginxionS

Агент держит один поток syslog и один CEF и открывает сокет только к IPv4-адресу (`logging.cc`, `socket_is.cc`).
Триггер журнала с одним IPv4-сервером агент обслуживает сам. Остальные случаи — несколько серверов, имя хоста,
IPv6 — обслуживает ретранслятор NginxionS (`waf/syslog.js`):

- в политике агента сервер триггера заменяется на `127.0.0.1:79xx` по UDP (контейнеры `nginxions` и `openappsec`
  делят сеть);
- backend NginxionS слушает этот порт и пересылает каждое сообщение всем серверам триггера: по UDP датаграммой,
  по TCP — с подсчётом октетов, как сам агент; TCP-соединение переподключается, пока сервер недоступен, сообщения
  ждут в очереди (до 1000);
- триггеры с одинаковым набором серверов делят один ретранслятор.
