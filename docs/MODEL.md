# Модель WAF NPMOS: обучение, проверка, выпуск

NPMOS обучает модель open-appsec сам: на открытых размеченных данных, в своём CI, на настоящем агенте. Готовая
модель — файл `open-appsec-advanced-model.tgz`, который ставится так же, как продвинутая модель Check Point:
**WAF → Агент → Модель → Загрузить** (`PUT /api/npmos/waf/agent/model`). Ни регистрации, ни облака.

## Как устроена модель open-appsec

Модель — один файл `/etc/cp/conf/waap/waap.data` агента:

- **сигнатуры** (`waap_signatures`): около 1 200 регулярных выражений. Они превращают значение запроса (параметр,
  заголовок, тело, cookie) в список **ключевых слов**: `<script`, `union`, `../`, `$(`…;
- **оценки** (`waap_scores`): вес каждого ключевого слова и пары соседних слов.

Штатная («базовая») модель считает оценку значения по счётчикам: сколько раз слово встречалось в атаках и в
легитимном трафике. Продвинутая — **разреженная логистическая регрессия** с признаками «есть/нет»:

```
оценка = 10 · sigmoid(intercept + log_nnz_coef · ln(n + 1) + Σ coef(признак))
```

где признаки — ключевые слова значения и их пары, `n` — их число. Слово, которого нет в модели, весит 0,3, пара —
0,8. Агент поддерживает такой формат сам (`isLinModel` в `ScoreBuilder`), поэтому **наша модель не требует правок
агента**: мы обучаем коэффициенты и записываем их в тот же `waap.data`. Сигнатуры остаются штатные.

Решение о блокировке агент принимает по **итоговой** оценке: оценка значения × поправка на **репутацию
источника** × поправка обучения (`D2Main.cc`), затем сравнение с порогом уверенности политики (`high`,
`critical`…).

## Что мы измерили

Первый прогон в CI (ветка с этим циклом, 15% легитимного набора): отложенная часть — 40 665 легитимных запросов
сайтов, которых модель не видела, и 22 072 атаки; у каждого запроса свой источник, политика `high`:

| | Штатная модель |
|---|---|
| атаки заблокированы | 99,36% |
| легитимные пропущены | 73,99% — **каждый четвёртый обычный запрос реального сайта блокируется** |
| безобидные «похожие на атаки» тексты mgm пропущены | SQLi 0%, XXE 0%, Shellshock 25%, cmdexe 78% |

Штатная модель ловит почти всё, но ценой ложных блокировок. Первая обученная модель на тех же данных офлайн:
99,3% атак и 99,7% легитимных; цифры её прогона через агент — в отчёте `training.yml` (первый прогон выявил две
ошибки стенда, обе закрыты проверками «осмотр» и «совпадение оценок», см. ниже).

## Цикл обучения

`training.yml` (ветка `training/<что угодно>`, `[train]` в сообщении коммита или Actions → Training → Run
workflow) → `scripts/train-model.sh`:

1. **Данные** (`model/datasets.py`):
   - `legitimate.zip` WAF Comparison Project — записанные сеансы 692 реальных сайтов (Amazon, Airbnb, Adobe…),
     7,3 ГБ; по умолчанию берётся 15% запросов (`legit_fraction`);
   - `malicious.zip` — 74 000 атак: XSS, обход путей, выполнение команд, SQLi, Log4Shell, Shellshock, XXE;
   - ложные срабатывания `mgm-web-attack-payloads` (из исходников в ветке `main`);
   - свои случаи: `model/cases/*.json` (`{"label": 0|1, "category": "...", "requests": [...]}`) — обходы, которые
     мы встретили, и легитимный трафик, который блокировался.

   Деление на обучение и проверку (70/30) — **по сайтам и полезным нагрузкам**, а не по запросам: проверочная часть
   состоит из сайтов и атак, которых модель не видела. Иначе мы измеряли бы, как модель запомнила данные.
2. **Стенд**: прод-стек из образов этой ветки, настроенный через API как администратором: сайт `train.local` без
   фильтра эксплойтов nginx, политика `prevent` (без обучения на ходу), источник — заголовок `X-Forwarded-For`.
   CrowdSec не запускается (он забанил бы раннер за атаки набора).
3. **Прогон штатной модели** (`model/replay.py`): каждый запрос набора идёт через nginx и агент со своим
   `X-Npmos-Sample` и своим адресом источника. Агент сам записывает, что нашёл в каждом значении (патч
   `0005-feature-dump-for-training.patch`: ключевые слова, пары, оценка). Патч пишет только в каталог
   `/var/log/npmos-features`, который есть лишь на стенде обучения; в обычной установке он ничего не делает.
4. **Обучение** (`model/train.py`): логистическая регрессия по признакам из выгрузки агента. Значения легитимного
   запроса — легитимные; в атаке вредоносным считается значение с наибольшей оценкой штатной модели (остальные её
   значения не используются). Порог: по прогону штатной модели находится оценка, с которой агент начинает
   блокировать; свободный член подбирается так, чтобы на обучающей части сбалансированная точность при этом пороге
   была наибольшей. Пары особого типа (тип 3) агент всегда считает с весом 0,8 — тренер тоже.
5. **Установка как в GUI**: `.tgz` загружается через API «WAF → Агент → Модель», агент перезапускается, стенд
   проверяет, что в агенте модель `NPMOS <ветка>-<номер прогона>`.
6. **Прогон новой модели** на проверочной части и **решение о выпуске** (`model/evaluate.py`).

## Когда модель можно выпускать

Все условия сразу, на проверочной части, по решениям **настоящего агента**:

- **осмотр**: каждый проверочный запрос, в котором агент нашёл ключевые слова со штатной моделью, дошёл до агента
  и с новой (≥ 99,5%). После перезапуска агента рабочие процессы nginx подключаются к нему по одному, и не
  подключившийся пропускает запросы без проверки (fail-open); стенд ждёт, пока атаки блокируются во всех, но
  проверка ловит и то, что он пропустил;
- сбалансированная точность (среднее «атаки заблокированы» и «легитимные пропущены») не ниже штатной;
- доля пропущенных легитимных запросов не ниже штатной больше чем на 0,2 п.п.;
- доля заблокированных атак не ниже штатной больше чем на 0,5 п.п.;
- **совпадение оценок**: оценка, которую агент поставил каждому значению с новой моделью, равна оценке, которую
  считает `model/waapmodel.py` по тем же признакам (≥ 99,9% значений с точностью 0,001). Если нет — агент читает
  модель не так, как её обучали, и цифры выше ничего не гарантируют для следующей модели.

Итог — в Summary прогона («Модель WAF: ✅ можно выпускать / ❌ не выпускается»), полностью — в артефакте
`waf-model`: `out/open-appsec-advanced-model.tgz`, `out/model-card.json` (порог, параметры, главные признаки,
офлайн-метрики), `metrics.json`, `report.md`, решения обоих прогонов.

## Выпуск

Модель, прошедшая проверку, выпускается руками: `.tgz` из артефакта прикладывается к релизу GitHub с карточкой
модели и отчётом. Администратор ставит её в **WAF → Агент → Модель**; вернуться к штатной — удалить модель там же.

## Чего модель не делает

- **Ноль риска недостижим.** Гарантия процесса другая: каждая выпущенная модель не хуже предыдущей на
  фиксированной проверке, а каждый найденный обход становится случаем в `model/cases/` и проверяется в каждом
  следующем обучении.
- Модель видит только то, что нашли сигнатуры. Атака, в которой агент не нашёл ни одного ключевого слова, для
  любой модели невидима: таких атак `model-card.json` показывает отдельно (`attacks_without_keywords`). Это
  работа для сигнатур, разбора запроса агентом (сжатое тело, необычные кодировки) и других слоёв: CrowdSec,
  схема OpenAPI, правила nginx.
- Метрики WAF Comparison Project и наши нельзя сравнивать напрямую: WCP шлёт все запросы с одного адреса, и на
  итог влияет репутация источника; у нас у каждого запроса свой источник.

## Локальный запуск

```bash
python3 -m venv .venv && .venv/bin/pip install -r model/requirements.txt
.venv/bin/python -m unittest discover -s model          # формат, данные, цикл на синтетике
curl -sSfLO https://downloads.openappsec.io/waf-comparison-project/malicious.zip
python3 model/datasets.py --malicious malicious.zip --out samples.jsonl
# образы с патчем 0005: scripts/build-images.sh (долго: агент из исходников)
NPMOS_REGISTRY=local NPMOS_VERSION=dev SAMPLES=samples.jsonl PYTHON=.venv/bin/python scripts/train-model.sh
```
